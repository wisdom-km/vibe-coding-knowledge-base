# 04 · 别人给的建议，先放进地图

边做边问人、问 AI，这是正常的。麻烦的是：建议进了下一句 Prompt，没进仓库。三个月后新开对话，谁也不记得那天到底答应过什么。

我们后来固定成一个很笨的循环：

有痛，或外面来了一条建议。  
先写成一张短卡，和现在的地图对一下，看冲突在哪。  
人来勾：吸收、推迟、只进知识库、或者拒绝。  
AI 只改被点名的那几份 md。  
下一场对话读仓库，不读那次咨询的聊天。

## 三种东西别写混

产品仓库里的开发地图，写的是**现在必须遵守的**：边界、落点、下一步。别把三年后的愿望写进去。

这个知识库，写的是**换项目还能用的**判断。别把某个产品的 Command 清单、函数签名抄过来。

聊天什么权威都不是。探讨可以，拍板不行。

专业人士和模型说的，默认都是草案。写进地图或知识库之后，下一场 vibe coding 才许执行。

## 建议来了，先打个标签

控制面：单向依赖、命令和快照、第三方别漏进公共头。这类几乎总该进产品地图。  
领域名词：剧本、机位、画布。和愿景冲突就先改愿景，否则改落点说明。  
空房间：空插件、空微服务、还没批准的供应商。默认拒绝，或只在知识库里记「以后可能需要的接缝」。  
过程：怎么和 AI 合作、怎么验收。进知识库，别写进产品契约。  
局部实现：这个 bug 怎么修。记进项目的现状日志就够，不必上升成跨项目教训。

## 怎样算没沉淀

咨询完直接让 AI 重构。  
把专家长文整篇贴进 Cursor Rule，改一处忘改另一处。  
产品地图和知识库互相复制签名。  
每来一条建议就新建一个模块。

三个月后，不贴那天的聊天，只 clone 仓库：Agent 还会不会遵守这条建议？不会的话，建议还在聊天里。

填卡可以用 [advice-intake.md](../docs/templates/advice-intake.md)。
