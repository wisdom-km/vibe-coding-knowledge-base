# 教训：专家建议进地图，不进下一句 Prompt

**来源**：[DirectorDesk / mira_new](../projects/mira_new/)；工作法：边做边优化，咨询专业人士与 AI，再整理成适合 vibe coding 的 md  
**适用**：所有「边做边听建议」的人机协作项目

## 模式

可重复的沉淀循环：

```text
痛点或外部建议
  → 写成建议卡（与现有地图对照）
  → 人决定：吸收 / 推迟 / 拒绝 / 只进知识库
  → AI 只改被指定的那一类文件
  → 下一场对话读仓库，不读那次咨询聊天
```

三类文件，禁止混写：

| 类型 | 放哪 | 写什么 | 不写什么 |
|------|------|--------|----------|
| 产品现行法 | 项目 `docs/dev-map/`（或同等） | 现在必须遵守的边界、落点、下一步 | 三年后的愿望、未批准的重构 |
| 可复用知识 | `vibe-coding-knowledge-base` | 跨项目的模式、反模式、提示词 | 该产品的 Command 清单、函数签名 |
| 聊天 | 无处 | 一次性探讨 | 任何权威 |

专业人士和 AI 的建议默认都是**草案**。只有写进产品地图或知识库对应文件后，下一场 vibe coding 才允许执行。

## 建议分类（决定写进哪）

收到一条建议时，先打标签：

1. **控制面**（单向依赖、命令/快照、第三方隔离）— 几乎总是吸收到产品 `01`/`08`  
2. **领域名词**（剧本、机位、画布…）— 与 `00` 冲突则先改愿景，否则进 `07` 落点  
3. **空房间**（空插件、空微服务、未用的供应商）— 默认拒绝或只记入知识库「以后的接缝」  
4. **过程**（怎么和 AI 合作、怎么验收）— 进知识库 `lessons/` / `prompts/`，不要复制进产品契约  
5. **局部实现**（这个 bug 怎么修）— 进项目 `03` 工作日志，不必进知识库  

## 反模式

- 「咨询完直接让 AI 重构」  
- 把专家长文整篇贴进 Cursor Rule（第二个事实源）  
- 产品地图和知识库互相复制签名  
- 每来一条建议就新建一个模块  

## 检验问题

三个月后新开对话、不贴那次咨询记录：Agent 是否仍会遵守这条建议？若否，建议还在聊天里，没有沉淀。
