# 教训：为变化预留接缝，不为幻想预留房间

**来源**：[DirectorDesk / mira_new](../projects/mira_new/)  
**适用**：任何准备用 vibe coding 做会加会删功能的项目，无论是不是 C++。

## 模式

架构要回答的是「哪一块可以独立加、独立删、独立坏」，不是「三年后每个按钮在哪」。

预埋这些：

- 模块怎么说话（接口 / 命令 / 快照）
- 数据归谁管
- 失败时如何降级
- 谁有权改哪一块（对 AI 来说就是构建图 + 文档地图）

不要预埋这些：

- 空表、空服务、空供应商 SDK
- 为假想功能新建的模块
- 5 人团队的 30 个微服务

## 反模式

「高度模块化」被理解成文件夹数量。结果是透传包装、空岛无限生长、一个小按钮改八处还改不干净。

正确收敛：控制面保留，模块数可以锁定，空岛冻结。

## 检验问题

设计评审只问：关掉它要改几处？主路径还能否走完？用户数据谁拥有？答不上来就不要合进主干。
