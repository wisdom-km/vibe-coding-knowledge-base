# 做完之后怎么收

P0 走完，开始问：还能不能撑以后加加减减？现在该全拆模块，还是锁住？vibe coding 哪些能做、哪些不能？

现行说法是部分模块化、停止扩张。控制面留着：单向依赖、Command 和快照、第三方关在 backends、状态只在主线程改。主路径那些模块当落点。AI 冻结。Link 就是一张薄表，不合并也不往里堆。不为小功能新建库。`Application.cpp` 厚就先厚着，痛了再在 App 里面拆文件。

加功能填进已有名词。删功能从入口剥到快照字段，别只藏按钮。好处是故障域清楚、换实现有地方放、下一场对话有地图。坏处也实在：App 会厚，快照会胖，加一个按钮要跨几层。切错边界时一个需求改五个模块——那该重切名词，不是再拆一个库。

能做的：先交地图再写窗口；用 CMake 挡错依赖；新预设、新命令、新面板、新加载器。不能做的：用聊天覆盖地图；在面板里解析剧本或调 bgfx；为假想功能建空服务；冻结解开前接线真 AI。

0-1 的时候名词已经写在愿景里，所以按用户路径拆模块不是过早抽象。P0 之后再「更模块」才是错的。大公司那套分层和所有权，一个仓库能做八成。功能开关和插件，是用户规模到了再加的缝。

加是插上一块，删是拔掉一块。每刀都要切开整栋楼，就回去补接缝，别再催功能。
