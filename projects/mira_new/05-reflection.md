## 1. 这个阶段的目标是什么？

回答三件事：这套 0-1 架构能不能撑长期迭代；现阶段全模块化还是部分模块化；vibe coding 哪些能做哪些不能。

## 2. 结论（现行政策）

**部分模块化，停止扩张。**

- 控制面全留：单向依赖、Command/快照、第三方关在 backends、主线程独占状态  
- 主路径模块保留当落点：Script / Scene / Camera / Asset / Storyboard / UI / Export / App  
- AI 冻结为空岛；Link 保持薄表，不合并也不长大  
- **禁止**为小功能新建 CMake 库；**暂缓**拆 `Application.cpp`  
- 加：填进现有名词。删：入口 → Command → visit → 快照字段，避免 DTO 墓地  

产品仓库：[`07-ITERATION-AND-LANDING.md`](https://github.com/wisdom-km/mira_new/blob/main/docs/dev-map/07-ITERATION-AND-LANDING.md)、[`08-SEAMS-AND-VIBE-CODING.md`](https://github.com/wisdom-km/mira_new/blob/main/docs/dev-map/08-SEAMS-AND-VIBE-CODING.md)。

## 3. 为什么这么做：好处与弊端

**好处**

- 主路径在功能进进出出时仍能走完  
- 故障域清楚（闪屏在 Renderer，路径在 Platform，布局在 Storyboard）  
- 换实现有落点（新格式 = 新 Loader）  
- 下一场 AI 对话有地图，不必考古聊天  
- 删除有分层  

**弊端（必须付）**

- App 厚、快照胖  
- 加一个按钮要跨三层，比在当前文件写 if 慢  
- 切错边界时一个需求改五个模块——应重切名词，不是再拆库  
- AI 空岛有心智成本  

不选的路：退回单文件（记忆一丢就缠死）；继续拆第 14 个库（Demo 税）；为假想功能建空房间。

## 4. Vibe coding 如何设计架构：能 / 不能

**能**

- 先提交宪法和 DAG，再写窗口  
- 用 CMake 当 AI 的团队边界  
- 新预设、新 Command、新 Panel、新 `IModelLoader`  
- 按层删除功能  
- 代码与地图冲突时停工  

**不能**

- 用聊天覆盖 `docs/dev-map`  
- 在面板里解析剧本、算机位、curl 供应商、调 bgfx  
- 为单个按钮或三年后的功能新建库/空服务  
- 接线真实 AI（冻结解开前）  
- 跳 Phase 做 Undo、时间轴、自由画布  
- 把知识库再抄成第三份架构正文  

## 5. 对「合适的设计路线」的复盘

0-1 时名词已经写在 `00` 里，所以**提早按用户路径拆模块是对的**——不是过早抽象，是宪法已在。

P0 完成后再继续「更模块」就是错的。路线应切换为：锁接缝、填名词、观察编排层是否真痛。

大公司的分层、接口、数据所有权，用一个仓库就能做 80%。功能开关、插件、多团队值班，是用户规模到了再加的接缝，不是 Demo 标配。

## 6. 可复用的经验

1. **地图先于代码，代码结束改地图。**  
2. **第二实现 / 第二调用方出现时才抽接口**（渲染、加载器都符合）。  
3. **编排者可以厚；领域模块必须瘦且有主人。**  
4. **知识库指向产品地图，不复制签名。**  

## 7. 给未来自己的一句话

加功能是插上一块，删功能是拔掉一块；若每刀都要切开整栋楼，回去补接缝，不要再催功能。
