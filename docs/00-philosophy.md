# 为什么要记

Vibe coding 生成很快。真正容易丢的是：当时为什么这么选、哪一步翻了车、哪条红线是故意画的。

聊天记录会关。脑子会忘。所以这个仓库按「阶段」来记——一次只写一段路上发生的事，不要试图写「整个项目回顾」。

## 记的时候可以想这几句

过程比结果值钱。三个月后你要的不是最终文件名，是「那天为什么没拆第十四个库」。

失败优先。能编译的成功案例到处都是；带着复盘的坑，下次才避得开。

写完问自己：这句能不能帮到以后的自己，或者另一个项目？不能的话，再收一收，别停在日记。

一次记一个阶段。跨项目反复出现的判断，另放到 `lessons/`；真用过的提示词放到 `prompts/`。

写清楚当时用的工具、模型、时间、约束。缺了这些，经验很快变成过时的鸡汤。

问过的人和模型，默认都不算数。你勾了吸收、推迟或拒绝之后，只改点名的那几份 md。产品地图写现在要遵守的，知识库写换项目还能用的，两处不要互抄细节。

## 和 vibe coding 的关系

感觉很好、但什么都没留下，是这类工作最常见的结局。记下来之后，下次不是从零开始，而是从「上次已经验证过的判断」开始。
