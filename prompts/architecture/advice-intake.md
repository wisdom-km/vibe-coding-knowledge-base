# 咨询完，先收成地图

刚和人、或另一个模型谈完架构、重构、专业化，用这一段。默认禁止改业务代码。

来自 DirectorDesk 后来固定下来的走法：边做边问 → 写成卡 → 人勾选 → 再改点名的 md。

```text
你在做一个已有开发地图的 vibe coding 项目。
刚才的讨论是草案，不是现行法。聊天记录不能覆盖仓库。

本次只做文档沉淀，不要修改 src/、include/、backends/ 等业务代码。

1. 把对方建议压缩成若干条「主张」，每条 3–7 句。
2. 对照仓库里现行的愿景、架构、现状、迭代政策；列出冲突表。
3. 给每条建议打标签：控制面 / 领域名词 / 空房间 / 过程 / 局部实现。
4. 等我勾选决定：吸收到产品地图 / 推迟 / 只进知识库 / 拒绝。
5. 只改我点名的 markdown。产品地图写「现在必须遵守的」；
   知识库写「换项目还能用的判断」，不要复制函数签名和 Command 清单。
6. 若建议等于空插件框架、空微服务、未批准的范围扩大：标成空房间，默认建议拒绝。
7. 结束时列出：改了哪些 md、哪些建议被拒绝、下一场对话应读哪些文件。

专业化的默认顺序：已经能走完的主路径先不动；只沿已有接缝把领域做深；
不要把 Maya / Unreal 的目录抄进来。
```

填卡用 [advice-intake.md](../../docs/templates/advice-intake.md)。
